# chat-ui

The sūveryn chat interface: React, TypeScript and Vite, light theme. It talks only to the gateway on the same origin and loads nothing from the internet: fonts and icons are bundled.

## Run it

```bash
npm ci               # exactly the versions in package-lock.json
npm run dev          # http://localhost:5173, proxies /auth, /v1 and /health to the gateway
```

Open it at **http://localhost:5173**: the gateway's `SUVERYN_PUBLIC_URL` and Keycloak's redirect URI use `localhost`. The gateway address defaults to `http://127.0.0.1:8000`; override it with `SUVERYN_API=http://host:port npm run dev`. In development the gateway usually runs on the GPU machine and is reached through an SSH tunnel:

```bash
ssh -N -L 8000:127.0.0.1:8000 -L 8180:127.0.0.1:8180 root@<gpu-host> -p <ssh-port>   # gateway and Keycloak
```

Other commands:

- `npm test`: unit tests (SSE parsing, answer rendering, copy and download, that the brand files match `suveryn-brand`, the web setup's text and rules, and the Content-Security-Policy rules: `src/csp.test.ts`)
- `npm run brand:sync`: re-copy the brand files from `suveryn-brand` (see below)
- `npm run typecheck`
- `npm run build`: static files in `dist/` (the chat, `index.html`, and the appliance's web setup, `setup.html`), plus `THIRD-PARTY-NOTICES.txt`

The web setup also runs on the dev server, at **http://localhost:5173/setup.html**, with example network settings when no appliance answers.

## The UI flow

0. **Sign in.** Signed out, the chat goes straight to the office's Keycloak login page (in the interface language), which already has the logo, tagline and language menu, and comes back signed in. Its own sign-in screen appears only when it has something to say: the session ended while working (redirecting then would discard what was being typed), sign-in isn't available (Keycloak unreachable), or the user came back signed out within a minute of being sent to the login page (the Back button, or a sign-in that didn't complete; redirecting again would loop) (`lib/signin.ts`). The account row at the bottom of the sidebar shows the signed-in user; its menu has *Sign out*, which also ends the Keycloak session. If a session ends (expired, or ended by an admin), the next request shows the sign-in screen again and the open conversation is closed.
1. **Start.** The start screen says "Welcome, <first name>" over the question box, with *Work in a case* to choose one of your open cases or start a new one. On first use (no conversations and no cases yet) two cards offer the two ways in, a question or a case, and the column says that recent chats and pins will appear there. The column (docs/design/chat-ui.md §2): *New*, the rows *Conversations*, *Cases* (with the number of open cases) and *Documents*, each opening its overview in the main area (the column lists no documents itself), then *Pinned* cases and personal conversations (the chevron on the left opens a case in place with its conversations) and *Recent* conversations (the icon says who sees it, the case reference is the meta), and the account row. Collapsed it is a rail of the same icons. Below 768 px the column is a drawer behind a menu button in a 56 px top bar that names the case and the conversation, targets are 44 px, and the composer is one pill with a "+" menu for the document, the playbook and the model.
2. **Ask about** (in a case, [docs/design/chat-ui.md](../../docs/design/chat-ui.md) §10, `ui/picker.tsx`, `lib/askAbout.ts`): beside the paperclip, *Ask about: all documents* ▾ chooses which of the case's sources the conversation's questions read; nothing chosen is the whole case. The choice stays for the conversation, is shown under each question, and the line under the question box follows it.
3. **Attach.** The paperclip adds a document to the next message as an attachment chip; opening a document in the *Documents* overview goes to its place with the document ready to ask about. A document is a PDF, Word (.docx), Excel (.xlsx), Markdown (.md) or CSV file (`lib/formats.ts`; the server checks every upload). In the composer each is a card (docs/design/chat-ui.md §5): uploading with its share, waiting and being read with a bar, then ready (with its pages), usable with the pages to check, failed with the reason and *Another file*, or sūveryn's own output with its choice. A question can be sent while a document is still read: it stays in the composer and counts for the next question once it is ready.
4. **Ask.** The question appears in the user's bubble, with the attachment chips above it. The answer streams in below, with no bubble, marked by the teal brand mark. Until the first word arrives, three small outlined squares, bouncing in turn, and a line of status text say what the server is actually doing: *Searching your documents…*, *Reading the 6 passages that best match your question…* (or *Reading your documents (n passages)…* when the whole document fits), *Loading Mistral Small 3.2, which can take up to half a minute…* when a switched model isn't in memory yet, or *Writing the answer…*. The squares stay at the end of the text while it streams. With reduced motion turned on, they don't move. While the answer is written, *Stop* takes the send button's place, and Esc does the same wherever the focus is (unless a menu or dialog is open). The question box stays usable, so the next question can already be typed. A stopped answer keeps what was written and the passages its markers point to, under the note that it is incomplete and unchecked; it is saved with the conversation, but not sent to the model as history for the next question. Under a finished answer, after its sources, a toolbar holds *Copy* (the answer and its sources), *Word* and, in a case, *Save to case*: it becomes a document of the case (origin answer, "Made", never a source), the toolbar then says where it was saved with *Open* and, during that visit, *Undo*; its Word file is built again from what was saved when it is downloaded from Documents (`lib/saved.ts`).
5. **Check the source.** Every `[n]` in the answer becomes a small teal marker. Clicking a marker, or a chip under *Sources*, opens the passage it came from in the source panel beside the conversation (440 px; over the page on a phone; Esc closes it and the focus returns to the marker; docs/design/chat-ui.md §5): file name, page and case, previous and next between the answer's sources, the stored text, and what the citation check found, in words (`lib/sources.ts`). The text is dimmed except what the claim rests on: the sentence on a teal wash, its figures, dates and names more strongly, and the passage scrolls to it (`lib/answer.ts`): for a marker, the claim before that marker; for a chip, every claim citing the source. The marker or chip whose source is open is filled teal. **Copy passage** in that panel copies the passage with its reference (`[1] file.pdf, p. 3 · Article 2` and the text below it); **Copy sources** copies every cited passage of the answer, numbered like the markers. **Download** next to each offers **Text (.txt)** or **Markdown (.md)** (one source: `source-1_deed_p3.txt`/`.md`; all sources: `sources_<question>.txt`/`.md`, headed by the question and the date). In Markdown the reference is a heading and the passage a block quote; the passage text is never altered. Both happen in the browser; nothing is sent to the server. Copied or downloaded passages are confidential and leave sūveryn's control: they sit on the clipboard or in the Downloads folder until the user deletes them. The answer can also show these notices:
   - *No source is cited…* when documents were used but nothing was cited;
   - *Not based on your documents…* when no documents were attached;
   - *Check …: these figures aren't in the documents and weren't calculated by sūveryn…* when the answer contains a figure in no source and no server calculation (`unverified_figures`); each such figure has a wavy ink underline in the answer;
   - *Calculated by sūveryn, not read from the documents…* under an answer with a total or other calculation, which the server computed exactly from figures in the sources (with a warning if a figure isn't in them).
4b. **Choose the model.** The model chip in the composer (`components/ModelPicker.tsx`) opens a small dialog (the component library's `ChipDialog`; a sheet from the bottom on a narrow screen): a `RadioList` of the models installed on this appliance (from `GET /v1/models`), each marked *Ready* or *Loads when you choose it*, and a `Segmented` choice of *Fast* or *Thorough* (thinking first; disabled, with the reason, for a model that can't think). Enter or Space opens it, the arrow keys move within each group, Tab goes from one to the other, and Escape closes it with the focus back on the chip. The chip shows the model and, with *Thorough*, the ink brain. The choice holds for the conversation. A model that isn't loaded makes the next answer wait while it loads (up to about half a minute), and the note under the composer says that other people's questions wait too, because the GPU holds one model at a time. With one installed model that can't think, the chip is a plain tag.
6. **Follow up.** Later questions in the same conversation automatically use every document attached so far; in a case, the *Ask about* choice. Each question is sent with the earlier questions and answers that completed; a question whose answer failed is left out. *New › New conversation* starts over. Deleting a document from the *Documents* overview asks for confirmation first.
5b. **Work in a case.** *Cases* in the sidebar (suveryn-tracker#10; the sidebar itself: docs/design/chat-ui.md) opens the Cases overview: every case you may see, open and closed, by the office's file number, with a search box, filters and a pin on each; a pinned case stays in the sidebar's *Pinned* section with its conversations under it. Documents and conversations outside any case are yours only; they appear in the same overviews without a case reference. *New* offers *New conversation* (personal, outside a case), *New case* and, in an open case you contribute to, *New conversation in case <reference>* first. *New › New case* asks for that number, a name (the hint says: no client's name on the label), the type (the notarial list as suggestions, or your own word) and a short subject, and opens the case. In a case the sidebar's conversations and documents are the case's, uploads go into it, questions are answered from its documents, and the header names it with your role. *Members* in that header lists who is in the case; its manager adds a colleague there from the office's accounts (a combo box that searches as you type) as a reader or contributor, changes roles, removes members, hands the case over (the previous manager stays as a contributor) and, on an office-wide appliance, restricts the case to its members or opens it. A reader can read the case but not add documents or ask (the composer says so). *Access log*, for the manager and the administrators, lists who did what in the case, newest first. An administrator who isn't a member sees a case exists and its manager, can hand it over and read its log, and nothing inside it. Its manager can delete it (with its documents and conversations) from that header, after a confirmation in which keeping it is the focused choice. Switching case starts a new chat there.

5c. **Close a case.** *Close case* in the header (its manager) asks for a confirmation that says what closing means: the case stays readable, nothing can be added, it can be reopened, and it is deleted after the office's keep period (named in the dialog: six months, a year, five years) or kept until someone deletes it. A closed case shows a lock in the sidebar and the header and a line under the header with when it was closed and what becomes of it (deleted on a date, due for deletion within a month, kept, or kept until deleted), with *Reopen* for its manager and *Extend* (one more period), *Keep* and *Let the period run* for the manager and the administrators. The composer says the case is closed. The full case list (*All cases…*) lists the closed ones under the open ones. Cases due for deletion are listed in *Administration › Cases*.

5d. **Share a conversation with the case.** A conversation in a case is yours until you share it: *Share with the case* in the header (a contributor or the manager, open case) lets the case's members read it, *Stop sharing* takes it back. Under a pinned case the sidebar lists your own conversations in it and the shared ones (a people icon). The Conversations overview lists yours and the ones colleagues shared with a case you may read, with the owner's avatar. Opening a colleague's shared conversation shows it read-only: the composer says who shared it and that you start your own to ask more; it is never saved over.

5e. **Administration.** *Administration* in the account menu opens a page with a side menu (`components/Admin.tsx`): *Users*, *Cases*, *Playbooks*, *Usage* and *Settings* for the office, *Status* and *Backups* for the appliance (on a narrow screen the menu is a page of its own). *Cases* lists every case on the appliance with its state, manager, member count and, for a closed case, when it is deleted (cases due within a month named above the list), and hands any case over to a colleague from the office's accounts. Above the list it shows the office's three settings, who sees a new case, how long closed cases are kept and how long conversations are kept, with *Change in Settings*: they are changed on the *Settings* page, and a change applies to new cases and to cases closed from then on.
7. **Come back to it.** After each answer the whole conversation is saved on the server, where only you can see it unless you share it (suveryn-tracker#5). *Recent* in the sidebar lists your eight newest, across your space and every case you may read, each with where it is; the *Conversations* row opens the overview of all of them, newest first, named after their first question (or the name you gave). Clicking one opens it again, in its place, and you can carry on. A document deleted since is left out of follow-up questions. The menu on each row, in *Recent* and in the overview, pins, renames, moves a personal conversation into a case, and deletes after confirmation. The browser keeps only two things (docs/architecture.md §3): the question being typed, in `sessionStorage` for this tab until it is sent or you sign out (`lib/draft.ts`), and preferences in `localStorage` (language, the collapsed column, *Fast* or *Thorough*, download formats). Without a database on the server, the sidebar says that conversations aren't saved and the conversation lasts as long as the page.
8. **Sign out.** With saved conversations, *Sign out* asks *Keep your chat history?*. *Keep and sign out* is the default and has the focus; *Delete history and sign out* deletes every saved conversation first (and stays signed in if that fails); *Cancel* or Escape stays signed in. Without saved conversations it signs out at once.

If the model is starting or unreachable, the composer says so and sending is disabled. If the server can't be reached, a bar at the top says so, that nothing is lost, and when sūveryn tries again, with *Try now*; the composer keeps the typed text. If the connection drops mid-answer, what arrived stays, marked as interrupted and unchecked; any other failure shows nothing of the attempt. Both offer *Regenerate*: the same question again, with the same documents.

## Tables, Word, Excel, Markdown and CSV

- **Tables:** a Markdown table in an answer is shown as a real table (`lib/answer.ts`), so copy and paste into Excel or Word keeps the columns. The model is told to answer with one when asked for a table, an overview or an Excel or Word file (`GROUNDED_INSTRUCTIONS` in packages/harness).
- **Word:** every complete answer has a *Word (.docx)* split button; its chevron offers *Markdown (.md)* as well, and the format last chosen becomes the default (`lib/downloadFormat.ts`). Both files hold:
  - the question and the date;
  - the answer, with its tables and lists;
  - what to check (calculations, figures, citations);
  - every cited source with its passage, or "Source deleted".
- **Excel:** every table has an *Excel (.xlsx)* split button, with *CSV (.csv)* in its menu (UTF-8 with semicolons, as Belgian Excel opens it; `lib/textfiles.ts`).
  - **The table sheet** has a frozen header and a last column naming each row's sources. Unambiguous amounts become numbers (`EUR 1.275.000,00` → 1275000 in euro format). Dates, references and anything ambiguous (`1.275`, `0123`) stay text. A column the model filled with source markers only is left out.
  - **The other sheets:** a sources sheet, and a sheet of what to check.
- **The sidebar** ([docs/design/chat-ui.md](../../docs/design/chat-ui.md), `components/Sidebar.tsx`, `components/Overviews.tsx`): one column that reads the same whatever is open. *New* (a conversation, a case, or a conversation in the open case); three rows, *Conversations*, *Cases* (with the count of open ones) and *Documents*, each opening its overview: a table of everything the person may see, with a search box, filter chips, a sort (or *Group by case*), 25 rows per page and a menu per row whose actions without the right are disabled, never hidden (`ui/table.tsx`: `DataTable`, `Pager`, `FilterSelect`, `FilterToggle`, `PinToggle`). A case's document and conversation counts open those overviews filtered on the case; a row opened goes to its place first. *Recent*: the eight newest conversations; *Pinned*: the cases the person pinned (their own choice, per user, on the server), each expanding to its conversations with an actions menu (open, unpin, members, access log, close); the account row at the bottom opens a menu with *My usage*, *Settings* (the picture; the password, a link to the office's sign-in), for administrators *Administration* and *Playbooks*, the language, and *Sign out*. The search icon opens one search across the three lists. The collapse icon folds the column to a 60 px rail of the same entries, remembered in this browser. In a case the pane is tinted (`case-surface`) under a header with the case, its type, the conversation, the members (the manager with the folder badge; opens *Members*), its document count (opens Documents filtered on the case) and its menu; the question box asks about the case and the line under it says answers use only that case's documents (a personal chat says only you see it). In a case with playbooks, an ink *Playbook* chip on a neutral surface, like the model chip, whose menu lists them with *Covered* (teal, with a check: a status) or *Not covered* (ink, with a triangle); the model chip wears an ink brain when *Thorough* is on.
- **Bron or Gemaakt** ([docs/design/chat-ui.md](../../docs/design/chat-ui.md) §6, `lib/origin.ts`, `lib/marks.ts`): every document says where it comes from (Documenten's *Herkomst* column and filter, the same icon wherever it appears); only a *Bron* is offered to a question. Word and Excel exports carry sūveryn's mark line; an upload that carries it shows a card ("Dit lijkt een antwoord van sūveryn") with *Toch als bron gebruiken* and *Verwijderen*, and isn't used until the person chooses.
- **Avatars** ([docs/design/avatars.md](../../docs/design/avatars.md), `ui/avatar.tsx`, `components/AvatarDialog.tsx`): the brand mark's rounded square with a fine `line` border; a picture, or ink initials on `surface-alt`; for administrators the outline of a shield in ink over the corner. A click on one's own avatar in the sidebar opens the dialog: choose a headshot, drag and zoom it inside the frame (never stretched), save; the browser sends the framed 512 px square and the server re-encodes it.
- **Deed intake** (suveryn-tracker#51, `components/DeedIntake.tsx`): the composer's *Playbook* chip (in a case that has one) opens the view, which takes the conversation's place. A contributor starts a run; the view polls it; at the checkpoint every fact is a row with its label, the value as read in a field, the source (file name and page) that opens the passage with the value marked, and the check's warning; *Confirm the facts* sends every row's value. Confirmed, the run offers a Word download of the facts (`intakeToWord`) and the summary appears among the case's documents, marked as sūveryn's own and never usable as a source. The fact labels are the playbook's vocabulary (`intakeFacts` in `i18n/`).
- **How the files are made:** in the browser (`lib/office.ts`) with [docx](https://github.com/dolanmiu/docx) and [write-excel-file](https://gitlab.com/catamphetamine/write-excel-file), both MIT. They load on the first download only, about 540 kB, and the chat itself stays about 9 kB larger. Nothing is sent anywhere. Their licences, and those of what they bundle, are in `THIRD-PARTY-NOTICES.txt` (`npm run notices`).

## Languages

The chat and the web setup share one list of languages and one current choice (`src/i18n/languages.ts`); each has one string table per language (`src/i18n/<lang>.ts`, `src/setup/i18n/<lang>.ts`), checked against the same copy rules (`src/i18n/rules.ts`). ## Components (suveryn-tracker#44)

Screens are built from a small component library in [`src/ui/`](src/ui/), shared by the chat and the web setup; every chat screen (the conversation, the sidebar, the dialogs, usage and administration) is on it. It sits on [React Aria Components](https://react-spectrum.adobe.com/react-aria/) (Adobe, Apache-2.0), which gives keyboard use, focus handling and screen-reader semantics, and has no look of its own; the look is `src/ui/ui.css`, from the brand tokens, through React Aria's `data-*` states (`[data-selected]`, `[data-focus-visible]`, …). Product screens use only `src/ui`, never React Aria directly; `src/ui/kit-only.test.ts` fails when one does.

| Component | For |
|---|---|
| `Button`, `LinkButton`, `CopyButton` | primary, secondary or quiet, or `plain` (behaviour only, for a screen's own pieces such as citation markers and chips); a link that looks like a button; copy with a *Copied* confirmation |
| `TextButton`, `IconButton` | a button that reads as a text link (Cancel, Keep, Sign out; with `link`, an underlined link in running text: the setup's Edit and Replace); a button with only an icon, its name also its tooltip |
| `TextField`, `PasswordField`, `TextArea` | label, hint and error tied to the field; a show/hide toggle; several lines (the question box) |
| `NumberField`, `DateField` | a number in the interface's language ("2,5" in Dutch and French); a date as day, month and year in the language's order |
| `Form`, `FormError` | errors shown on submit only (React 19 action), focus to the first field in error; a message for the whole form |
| `RadioCards`, `RadioList`, `Segmented`, `Checkbox` | one choice of a few, with the arrow keys (also short options side by side: the usage period); a yes or no |
| `Select`, `SelectField` | one value from a list (the language menu; a field in a form) |
| `MenuButton` | a menu that acts at once (a passage's download formats) |
| `ChipDialog` | a chip that opens a small dialog of choices that apply at once (the model and its thinking mode) |
| `Toolbar` | a row of related buttons, one Tab stop, the arrow keys between them (an answer's actions) |
| `ActionMenu` | a richer menu: items with an icon and a meta text, separators, a submenu, a header and fine print (the account menu, a case's actions, *New*, the composer's *Playbook* chip) |
| `Expander` | a row whose label opens something and whose chevron expands a panel under it in place (the sidebar's rows and pinned cases) |
| `Switch` | on or off, applied at once (a playbook's *Active*) |
| `ComboBoxField` | a text field with suggestions, for a value that may be the user's own (a case's type) |
| `SearchField` | a search box that filters a list (the full lists of cases, conversations and documents; the search view) |
| `FilePick`, `FileDrop`, `FileButton` | choose a file, or drop it on an area that also has a button to choose one; any button opening the file picker (the paperclip) |
| `Dialog` | a modal dialog: the focus moves in (to the safe choice) and back, Escape closes it unless it is busy |
| `Progress`, `StatusList` | a progress bar; a list of steps, each waiting, running, done or failed |
| `QrCode` | a QR code drawn as SVG paths (no image, so the CSP needs nothing extra) |
| `ColumnChart`, `BarChart` | columns over time and bars for comparison, up to two stacked series (suveryn-tracker#46): HTML with the brand's chart colours, round axis steps from d3-array; every chart can be shown as a table, the columns are one Tab stop with the arrow keys, Home and End, each read out with its values |
| `Avatar`, `IconBadge` | a person's picture or initials in the brand's rounded square, with the outline of a shield for administrators; a small badge over a picture's corner (the manager's folder and the owner's speech bubble on an avatar) |
| `Card`, `Steps`, `Note`, `Notice`, `InlineNotice`, `Facts`, `Rows`, `Chips` | layout, no behaviour (`InlineNotice`: a line with an icon, under an answer or on the sign-in screen; `alert` or `status` to have a screen reader read it) |

**The CSP.** How this UI keeps to the appliance's Content-Security-Policy, what to check before adding a library and what to do when the build stops with a CSP error: [docs/content-security-policy.md](../../docs/content-security-policy.md). `src/csp.test.ts` checks the source against its rules. In short: the appliance sends `style-src 'self'` without `'unsafe-inline'`. React Aria writes two `<style>` elements of its own, which the browser would refuse (and report): `src/ui/csp.ts` makes it skip the first (pressable elements), and a build step in `vite.config.ts` replaces the second (iPhone and iPad, while a menu is open) with an attribute; `ui.css` carries both rules instead. The build fails if a React Aria update changes that code. Style properties React Aria sets through the DOM (a popover's position) are allowed.

**Forms** use React 19's `useActionState`, started from `onSubmit`: given the form's `action`, React resets the form after each submit, and React Aria's fields follow the reset, which wiped every answer when Continue found an error. Fields don't use React Aria's built-in validation (`isRequired`, the browser's own `type="email"` check), whose messages come from the browser, in its language, and can appear while typing. Errors come from the screen's check, in the interface language, when the form is submitted.

React Aria's own strings (e.g. "selected") are kept for English, Dutch and French only (`@react-aria/optimize-locales-plugin`). The spike's measurements: [`docs/spikes/react-aria/`](../../docs/spikes/react-aria/README.md).

## The web setup (setup.html)

The appliance's first-boot setup in the browser (suveryn-tracker#37; design in suveryn-appliance `docs/design/first-boot-setup/`). Its own entry and bundle: `setup.html` and [`src/setup/`](src/setup/). It shares the component library, fonts and tokens with the chat and nothing else: no sign-in (setup creates the first account, so it can't depend on Keycloak), no chat code. The appliance serves it only until setup finishes.

- Laid out like the Keycloak login: the lockup and tagline, a 560 px card, the language menu in the card's top-right corner, the same focus ring.
- It asks the appliance `GET setup/v1/state` for what the console installer set (name, address, language), the appliance's ID and fingerprint, the installed models, the USB disks and the answers saved so far.
- Its text is in [`src/setup/i18n/<lang>.ts`](src/setup/i18n/), in English, Dutch (formal) and French (vous); the language starts as the one chosen at installation.

The screens ([`src/setup/steps/`](src/setup/steps/)):

0. **Welcome.** What setup asks, in six steps, and *Get started*.
1. **Network.** Connected (with approved destinations only, or everything) or Air-gapped.
2. **Administrator account.** Name, email address and password: at least 15 characters, not a common password, not the name, email address or appliance name. The password is sent to the appliance once and never kept in the page.
3. **Certificate.** The appliance's own (self-signed) certificate, or the office's: certificate, private key and optional chain as PEM files (64 KB at most each). The appliance checks that they belong together.
4. **Support agreement.** Register the appliance on the Sūveryn Labs portal (the link, a QR code with the same address as the console's, the ID and the fingerprint with copy buttons), then drop or choose the manifest the portal returns; its edition, users and dates are shown. *Skip for now* continues without one.
5. **Backups.** A USB disk, a network share (SMB or NFS, with *Test connection*, which checks that the appliance reaches the share's server on the office's network) or *Set up later*, and how long to keep backups. A backup goes to a USB disk or share only with a recovery key (below).
6. **Review.** Every answer, with *Edit* back to its step (which then returns here). The name is changed in the console only. *Start provisioning*.
- **Provisioning.** Each step with its state: the database, sign-in, the models, the web server, the outgoing-traffic check. A failed step says why and offers *Try again*. A reload picks it up where it is.
- **Complete.** What was set up, a warning if outgoing traffic turned out not to be limited, the sign-in address and *Open sūveryn*.

Every step is saved on the appliance when Continue is pressed (a reload resumes there), and the appliance checks everything again. The contract, with the error codes, is at the top of [`src/setup/api.ts`](src/setup/api.ts); the appliance answers it with suveryn-appliance's [`setup/`](https://github.com/suveryn/suveryn-appliance/tree/main/setup) (#37 part 5). Its refusals are shown in the interface's language (`errors` in `src/setup/i18n/<lang>.ts`).

**The backup recovery key.** The browser makes an [age](https://age-encryption.org) X25519 key pair (WebCrypto, `src/setup/recoveryKey.ts`) and downloads the private half as an age identity file (`suveryn-backup-recovery-key-<name>.txt`); only the public half (`age1…`) goes to the appliance, which encrypts backups to it. So the appliance can make backups but can't read them, and nobody can without that file. Setup continues only once the file has been downloaded and the administrator confirms it is stored safely. The format is checked against the real `age-keygen` in `screens.test.ts`.

**Without an appliance.** `npm run dev`, and the preview build `npx vite build --mode demo`, answer from [`src/setup/demo.ts`](src/setup/demo.ts) with the design's example values; a production build doesn't contain it (`screens.test.ts` checks the guard). In the demo any `.yaml` file is a valid manifest, a share address containing "fail" can't be reached, and adding `#check-fails`, `#provisioning-fails` or `#no-disk` to the address tries those cases. The browser check that walks every screen in all three languages, with axe and the real CSP: [`docs/spikes/react-aria/check.py`](../../docs/spikes/react-aria/check.py).

## Token usage

The sidebar shows the signed-in user's own token count for today (*1.2k tokens today*); clicking it opens **Your usage**: requests and input, output and total tokens over the last hour, day, week or month, or chosen whole days, with a chart of input and output tokens per step (also as a table) and a split by kind (suveryn-tracker#7, #46). Only the user's own usage is shown, never a colleague's. Administrators (Keycloak role `suveryn-admin`) also get **Administration › Usage**: the office's usage in total and **per user** (a bar per person, then the exact numbers in a table), and the notional cost on a cloud API at the rates per million input and output tokens (default $3 and $15), with who last changed them. The rates are changed on **Administration › Settings**. Rolling periods end at the server's clock, not the browser's. Usage is informational only: nothing is ever limited because of it.

## Languages

English (UK), Dutch and French (suveryn-tracker#8). Every string the interface shows is in a table per language in [`src/i18n/`](src/i18n/): [`en.ts`](src/i18n/en.ts) defines the keys, and [`nl.ts`](src/i18n/nl.ts) and [`fr.ts`](src/i18n/fr.ts) must have all of them. TypeScript checks that, so a missing translation fails the build, and a test checks that no text is empty. Components use `useT()`; plain functions use `t()`. No i18n library is used.

- **Which language:** the one chosen in the language menu (sidebar foot, the sign-in screen when shown, and Keycloak's own menu on its login page; remembered in this browser), else the browser's preferred language when it is one of the three, else English. `<html lang>` follows it. Keycloak's login page opens in the same language (`/auth/login?lang=nl` → `ui_locales=nl`).
- **Dutch is formal** (*u/uw*); a test fails on *je/jij/jouw*. **French** uses *vous*.
- **sūveryn** stays lower case except at the start of a sentence (also tested).
- **The tagline** stays in English in every language, as on the website and the login page.
- **Dates** follow the language (`en-GB`, `nl-BE`, `fr-BE`), also in downloaded sources.
- **What stays English:** most messages that come from the server (a calculation's error, a model server's error) and model names. The errors people meet most (too many requests, too large, not found, no permission, unavailable, an invalid request) are shown in the interface language by HTTP status (`httpErrorText` in `api.ts`). Answers are in the language of the question, whatever the interface language.

To add a string: add it to `en.ts`, then to `nl.ts` and `fr.ts` (the build tells you where).

## Brand elements

[suveryn-brand](https://github.com/suveryn/suveryn-brand) is the single source of the mark, favicon, fonts and design tokens. `scripts/brand-sync.mjs` copies them in at a pinned commit and generates `src/styles/tokens.css` from [`tokens/tokens.json`](https://github.com/suveryn/suveryn-brand/blob/main/tokens/tokens.json):

```bash
npm run brand:sync                 # re-sync at the commit in src/brand/brand-lock.json
npm run brand:sync -- <commit>     # move to a newer brand commit
SUVERYN_BRAND_REPO=../suveryn-brand npm run brand:sync -- <commit>   # from a local clone, before the commit is on GitHub
```

The copies are committed, so building never needs the internet. `src/brand/brand-lock.json` records the commit and a hash of each file, and `npm test` fails if one is edited by hand. Never edit `tokens.css` or the brand files directly; change `suveryn-brand` and re-sync.

**Colours are OKLCH** (brand tokens v3): every token in `tokens.css` is an `oklch()` value, exactly the colour its hex was, and every colour the library and the app derive from a token (a wash of the teal, a shadow or a dimmed border of the ink, the focus glow) is written as `oklch(from var(--token) l c h / alpha)`: the token's own hue and lightness with an alpha, never a new hex or rgba. The chart-colour test converts OKLCH to sRGB luminance (Ottosson's OKLab) for its contrast checks. Browsers draw both since 2023/24 (relative colour syntax: Chrome 119, Safari 16.4, Firefox 128), so there is no fallback.

**Text sizes come from the type scale** (brand tokens v3.2): `tokens.css` carries the brand's fourteen text styles as `--text-<style>` (the size), `--leading-<style>` and `--weight-<style>`, and the stylesheets say which style a thing has (`font-size: var(--text-ui-sm)`), never a pixel size of their own; `npm test` fails on a literal `font-size` in `app.css`, `ui.css` or `setup.css`. Weight and colour may vary within a style; size and family may not. Before v3.2 this UI had eighteen sizes of its own and the site fourteen; the scale is the fix for that drift.

## Brand rules this UI keeps

From the [brand guidelines](https://github.com/suveryn/suveryn-brand/blob/main/guidelines/brand-guidelines.md):

- Light theme tokens only (`src/styles/tokens.css`, generated from `suveryn-brand`).
- Only the user's turn has a bubble. The assistant's reply is marked by the teal brand-mark outline.
- Attachment chips (outlined, on the user's turn) and citation chips (teal, on the reply) are different components.
- Text and icons on the accent colour use `--on-accent`, never white.
- IBM Plex Mono is used only for the wordmark. Headings use Space Grotesk, everything else Inter.
- Icons come from Lucide. The model tag in the composer is neutral, a name with no vendor logo.
- UI copy is in UK English.
